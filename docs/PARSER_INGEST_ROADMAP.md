# Парсер Hunter — ingest, фильтры и масштаб (зафиксировано 2026-06-10)

> **Зачем документ:** при каждой итерации парсера, quality gate и Premium-фильтров сверяться с этим направлением.  
> Решение принято владельцем продукта: опасение **пропуска реальных вакансий** из‑за жёстких фильтров на входе и **пустых категорий** в ленте.

---

## 1. Как сейчас (baseline)

```text
Telegram-чаты → evaluate_vacancy() [жёсткий gate] → одна category_code в БД
              → push/лента по подписке на категорию → Premium-фильтры (geo, ставка, смена)
```

**На ingest отсекается** всё, что не прошло:

- gate «это заказ персонала» (контакт, не резюме, не спам);
- `detect_category` + `passes_quality_gate` (роль в тексте);
- дубликаты.

**Не попало в БД — потеряно навсегда** (кроме ручного аудита «примеры отсева»).

**На выдаче** уже есть второй слой — [`PREMIUM_FILTERS.md`](PREMIUM_FILTERS.md): гео, метро, ставки, тихие часы. Это **не** пользовательские ключевые слова «как в Юду».

---

## 2. Куда двигаемся (целевая модель — гибрид, не «лить всё»)

Ориентир — агрегаторы вроде **Юду**: единый поток → **персональная выдача**.  
Hunter **не** копирует «100% сообщений в БД», но **смягчает ingest** и переносит часть отбора на выдачу.

| Слой | Сейчас | Цель |
|------|--------|------|
| **Ingest** | Одна категория или reject | Сохранять всё, что **похоже на заказ персонала**, даже при спорной роли → статус `uncertain` / multi-tag |
| **БД** | `category_code` (один) | `category_code` (primary) + **теги/скоры** по ролям (`promoter:0.8`, `handyman:0.9`) |
| **Подписка** | Категории бота | Категории + **ключевые слова / минус-слова** (Premium) |
| **Push/лента** | `get_subscribers_by_category(code)` | Матч: `(категория ИЛИ keyword) И premium-фильтры` |
| **Backfill** | `/enrich_backfill` | + перекатегоризация при улучшении правил (уже частично есть) |

**Явно не делаем:** слив резюме, рекламы, «ищу работу», флуда без признаков заказа — иначе 1000+ сообщений/день/канал убьёт UX и диск.

## 3. Принципы для следующих итераций парсера

При правке `parser.py`, quality gate, категорий — **проверять:**

1. **Recall важнее precision на границе ролей.**  
   Спорный «разнорабочий vs охранник» → лучше **сохранить** с тегами, чем reject или одна неверная метка без возможности исправить.

2. **Не ужесточать gate без метрик.**  
   Перед новым reject-правилом: прогнать **аудит фильтра** (админка) и посмотреть `reject_samples` по чату.

3. **Пустая категория за неделю — сигнал**, не норма.  
   Причины: мало чатов на роль, gate слишком жёсткий, ошибка классификации (ушло в другую категорию).  
   Действия: покрытие каналов, audit, `/enrich_backfill 30`, точечное ослабление gate для категории.

4. **Одна ошибка классификации не должна ломать историю.**  
   До multi-tag: backfill категорий; в ленте не делать лишний re-check текста против `category_code` (уже убрано для feed/history).

5. **Premium-фильтры — продукт, не костыль.**  
   Расширять: keywords, «показывать если адрес неизвестен», ставка, район — вместо бесконечного ужесточения ingest.

6. **Сравнение с ручным просмотром каналов.**  
   Владелец видит ~1000 сообщений/день в канале; бот должен попадать в **большинство явных вакансий**, даже если категория спорная.

## 5. Масштаб: ~100 каналов, CPU и память (ЧПУ)

> Имеется в виду **процессор (CPU)**, не SEO-«ЧПУ».

### Как устроена нагрузка

- **Telethon realtime** — **одно** MTProto-соединение на все каналы; подписка на 100 чатов **не** = 100× CPU на «слушание».
- **CPU растёт от:**
  - числа **обрабатываемых сообщений в секунду** (пики утром/днём);
  - **`_parser_lock`** — разбор сообщений **последовательно** (очередь при всплеске);
  - **push** — Premium-подписчики × вакансии (уже в фоне, не в lock парсера);
  - **БД** — insert + dedupe + ленты/история;
  - **ширины ingest** — если сохранять больше строк, растёт **диск** и время SELECT.

### Оценка порядка величины

| Параметр | Оценка |
|----------|--------|
| 100 каналов × 1000 msg/день | ~100k msg/день ≈ **1–2 msg/с** в среднем, пики **10–30 msg/с** |
| Доля «похоже на вакансию» | часто **5–15%** → 5–15k оценок `evaluate_vacancy`/день |
| Типичная стоимость одной оценки | миллисекунды (regex), без LLM |

**Вывод:** сам по себе переход **до ~100 каналов не означает обязательный переезд на Timeweb**. Bothost/VPS с **512 MB–1 GB RAM** часто тянет такой поток, если нет тяжёлой очереди push и БД не раздута.

### Когда ресурсы становятся узким местом

| Симптом | Что делать |
|---------|------------|
| Парсер «отстаёт» на часы, lock постоянно занят | Очередь/worker, ослабить sync в hot path, апгрейд тарифа |
| RAM 90%+, OOM | Меньше кэшей, PG вместо SQLite, больше RAM |
| Диск БД | Retention (архив старше N дней), индексы, отдельный PG |
| Push лаг | Лимиты rate, digest вместо мгновенного push |

### Timeweb — когда имеет смысл

Перенос Hunter на Timeweb — **не автоматически при 100 каналах**. Критерии — в [`DEVELOPMENT.md` § Хостинг](DEVELOPMENT.md#хостинг-bothost-сейчас--timeweb-цель): монетизация, лимиты Bothost, общая PG с agency, webhook, операционка.

**Добавлено к критериям масштаба** (достаточно **одного** вместе с мониторингом):

- стабильный **lag парсера > 30–60 мин** в рабочие часы при 50+ каналах;
- **RAM/диск Bothost** упираются в потолок тарифа 2 месяца подряд;
- **>200 Premium** и push создаёт заметную очередь.

Timeweb даёт **стабильный PG, volume, деплой** — но **CPU нужно заказывать отдельно** (тариф App Platform / VDS). Переезд ≠ бесплатное ускорение.

### Рекомендация до 100 каналов

1. Оставаться на **Bothost**, пока нет симптомов из таблицы.
2. Смотреть логи: `parser lock`, время от поста до push, размер PG.
3. Перед расширением ingest — **заложить retention** (не хранить весь сырой шум вечно).
4. При росте — сначала **апгрейд тарифа Bothost**, потом решение про Timeweb по чеклисту в DEVELOPMENT.
