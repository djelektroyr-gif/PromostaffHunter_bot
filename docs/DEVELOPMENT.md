## 1. Назначение бота

Telegram-бот для исполнителей (хелперы, грузчики, промо и т.д.):

1. **Парсит** вакансии из групп через **Telethon** (`user_session`).
2. **Фильтрует** по релевантности, категории, дедупликации.
3. **Рассылает** подписчикам push по выбранным категориям (aiogram polling).
4. Даёт **отклик** (deeplink в личку заказчика с черновиком анкеты).

## 2. Архитектура (два контура)

```
Группы Telegram
    ↓ Telethon (user_session): события + опрос каждые 5 мин
parser.py → save_vacancy → send_vacancy_to_subscribers()
    ↓ aiogram Bot (BOT_TOKEN): polling
main.py → кнопки, админка, профили, отклики
    ↓
SQLite bot_database.db  **или** PostgreSQL (`DATABASE_URL`)
```

| Компонент | Файл | Роль |
|-----------|------|------|
| UI бота | `main.py` | Команды, FSM, рассылка, админ-меню, «Мои данные» |
| Парсер | `parser.py` | Telethon, фильтры, категории, dedupe |
| Фото профиля | `profile_photos.py` | Скачивание в `user_photos/`, отправка, health-check `file_id` |
| БД | `db.py`, `db_backend.py` | SQLite локально / PostgreSQL на Bothost prod |
| Настройки | `config.py`, `.env` | Токены, список чатов по умолчанию |
| Тесты | `tests/test_*.py` | Парсер, подписка, профиль, лента |

**Важно:** один процесс на файл `user_session` — второй инстанс ломает парсер.

## 5. Парсер — как работает сейчас

### Потоки

1. **Старт:** `start_realtime_listener()` — Telethon + стартовый scan + плановый опрос **каждые 300 с**.
2. **Real-time:** `NewMessage` только если `chat_id` в `_monitored_chat_ids` (резолв из БД).
3. **ID вакансии:** единый `make_vacancy_id()` (md5 16 символов от `dedupe_key` или `chat_id_message_id`).

### Фильтры

- `is_job_post_for_staff()` + `evaluate_vacancy()` — общий gate (найм + оплата + контакт) и per-category `passes_quality_gate` для всех 11 категорий; без fallback в helper.
- **Digest (P1):** нумерованный пост «1. … 2. …» → `should_split_digest()` → каждый блок отдельно через `_save_parsed_vacancy_block()` (свой `dedupe_key`, id `{message_id}_b{N}`); целый пост не проходит `evaluate_vacancy` (`digest_split_required`).
- `detect_category()` — scoring по тексту; `None` если роль не уверена.
- Push и лента: `evaluate_vacancy()` / `vacancy_matches_category()` — перепроверка перед отправкой.
- Dedupe: exact по `dedupe_key`, fuzzy ~82% + телефон.
- **Окно свежести** — `is_message_recent()` (по умолчанию **36 ч**, env `VACANCY_MAX_AGE_HOURS`), не «только сегодня» МСК.

### Устойчивость парсера

- **Reconnect:** при обрыве Telethon переподключается каждые 30 с.
- **Health loop:** каждые 10 мин — проверка online и `monitored vs active_chats`; алерт админу не чаще 1 раз/час; авто-`refresh_monitored_chat_ids`.
- **Session lock:** `session_lock.py` — второй процесс на `user_session` не стартует.
- **check_now / get_new_messages:** только shared client, без временного второго Telethon.

### Задержка push (важно для продукта)

**Два канала доставки:**

1. **Realtime** — `events.NewMessage` в Telethon (должен быть почти сразу после поста в канале).
2. **Резерв** — полный проход по чатам каждые **300 с** (`PARSER_POLL_INTERVAL_SEC`), до **120** сообщений на чат.

**Почему в чате «пачками» и с лагом ~30–60+ мин (типичный кейс):**

- Раньше парсер **ждал** окончания `send_vacancy_to_subscribers` (1 с × число Premium-подписчиков на каждую вакансию) **в том же потоке**, что и разбор канала → очередь из десятков постов копилась.
- Плановый скан мог отдать **пачку** вакансий разом после прохода по всем чатам.
- В карточке **«Опубликовано»** — время поста в UTC; в Telegram-канале отображается **МСК** (+3 ч), из-за этого кажется «бот опоздал на 3 часа».

**С 2026-06-04:** push через `schedule_vacancy_push` (фон, до 2 параллельных рассылок); в UI — **«… МСК»**.

**Проверка на проде:** в логах `⚡ Парсер групп: новое сообщение chat_id=…` — realtime; `🔄 Плановая проверка: новых вакансий N` — каждые ~5 мин (даже при N=0). Если только `Got difference for channel` без `⚡` — опора на плановый incremental-скан.

**Bothost / session:** без `user_session.session` парсер **не работает** (бот отвечает, вакансии не копятся). Файл: `/app/shared/user_session.session` или `/app/user_session.session`. Первая строка в логах: `Telethon session: …` — путь должен существовать.

### Фильтр метро (Premium)

- Поле `subscribers.metro_zones` (через запятую).
- Кнопка **📍 Мои районы** — push и лента фильтруются по станциям; если в вакансии метро не указано — не отсекаем.

### Известные ограничения парсера

- [ ] Категории по ключевым словам — scoring, без ML (P3: feedback).
- [x] Digest «1. … 2. …» — **split по блокам** (P1, `tool-v1`); reject только блоки, не прошедшие gate.
- [x] P0: `evaluate_vacancy()` — staff gate + per-category quality; push re-check.
- [x] Закрытие вакансии — reply «закрыто», строка «ЗАКРЫТО» в посте, зачёркивание (MessageEdited).

**Классификация (2026-06-05):** «координатор свадеб/организатор» ≠ супервайзер; отдельно «промо», «выгрузка/фасовка/рохля» → грузчик; без оплаты — не в ленту; fuzzy-dedupe ловит повторы одной кампании с разными адресами.

## 8. Антиблокировка (обязательно соблюдать)

### Bot API

- Push-вакансии: пауза **~1 с** между получателями (`SEND_DELAY`).

- Не слать заблокировавшим бота; учитывать `is_active`.
- Кнопка «Отписаться».

### Telethon

- **Один** процесс на `user_session` — `session_lock.py`, алерт при втором инстансе.
- Аккаунт парсера — член групп, без спама.

## 9. История критичных исправлений (не забыть)

| Проблема | Решение |
|----------|---------|
| Задержка вакансий ~3 ч | Резолв chat_id, плановый опрос 5 мин, shared Telethon |
| Разные ID вакансии в БД и кнопках | `make_vacancy_id()` везде + миграция legacy ID при старте |
| `respond_add_` ломался | Фильтр callback exclude `respond_add_` |
| Закрытие вакансий не уведомляло | `mark_vacancy_closed` по message_link + notify в realtime/scan |
| Категория упаковщик → parking | Переписан `detect_category` (scoring + tie-break) |
| Free получал push как Premium | Push только `is_user_premium()` |
| Второй процесс ломал Telethon | `session_lock.py` |
| Парсер offline без алертов | Health loop + auto-reconnect |
| «Только сегодня» отсекало вечер | `is_message_recent` 36 ч |
| Нет фильтра метро | `metro_zones` + 📍 Мои районы |
| Telethon EOF на сервере | `create_authorized_client()` — connect без input(); алерт если нет `.session` |
| `TypeNotFoundError` / Constructor ID | Обновить `telethon` в `requirements.txt`; один `.session` на один процесс; авто-reconnect 30 с |
| Конфликт `cat_` postvacancy vs регистрация | Префикс `postcat_` для админ-публикации |

## 11. Деплой и проверки

1. Локально: `python -m pytest tests/ -q`
2. **Telethon-сессия (обязательно на проде):**
   - Локально один раз: запустить бота → создаётся `user_session.session`
   - Аккаунт парсера — **участник** всех групп
   - **Bothost ([bothost.ru](https://bothost.ru/)):** включить «Общее хранилище» у бота → редеплой → загрузить `user_session.session` в «Общие файлы» → путь `/app/shared/user_session.session` (авто, см. `SHARED_DIR`)
   - **Timeweb / свой VPS:** volume или `/app/user_session.session`
   - Env: `API_ID`, `API_HASH`; при нестандартном пути: `TELEGRAM_SESSION_NAME=/app/shared/user_session`
   - Без `.session` парсер не стартует (бот для пользователей работает)
3. **База данных:**
   - **Локально / dev:** SQLite (`bot_database.db` в корне проекта или `DATABASE_PATH`).
   - **Bothost prod:** **PostgreSQL** через `DATABASE_URL` (managed DB) — **текущий прод с 2026-06-05**.
   - **Bothost prod (legacy SQLite):** «Общее хранилище» → `/app/shared/bot_database.db` — только если PostgreSQL не используется.
   - Перед деплоем: бэкап БД (файл или pg_dump).
   - Env SQLite: `DATABASE_PATH=/app/shared/bot_database.db`
   - Env PostgreSQL:
     ```env
     DATABASE_URL=postgresql://user:password@host.example.com:5432/promostaff_hunter
     ```
     При первом старте `init_db()` создаст таблицы и засеет категории/чаты автоматически.
4. На сервере: **один** процесс бота, `user_session.session` на месте
5. После выката: `/start` → **📊 Статистика** — строка парсера ✅, не «нет файла session»
6. **📋 Список чатов парсинга** — все активные группы ✅
7. Тестовая вакансия: push → «Откликнуться» → deeplink

### 11.1 SQLite vs PostgreSQL (Hunter)

| | SQLite в `/app/shared` | PostgreSQL (`DATABASE_URL`) |
|---|------------------------|----------------------------|
| Сложность | Работает из коробки | Managed DB на Bothost + env |
| Bothost prod | SQLite legacy в shared | **PostgreSQL** (`DATABASE_URL`, текущий прод) |
| Масштаб | Dev / fallback | Prod Bothost с 2026-06-05 |
| Локально | **По умолчанию** (без `DATABASE_URL`) | Опционально для проверки prod-схемы |

Код поддерживает оба бэкенда через `db_backend.py`. Без `DATABASE_URL` — SQLite как раньше.
